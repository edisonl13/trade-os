# TRADE//OS 统一多平台导入规则

日期：2026-07-28  
状态：第一版产品与数据边界已确定；平台细节按真实样本逐步补充

## 决策

TRADE//OS 不以 FX、股票、期货、加密货币或任何单一券商为中心。导入流程先判断文件记录的是什么，再判断来自哪个平台。

平台名称只决定字段适配方式，不决定产品能否分析。任何来源最终都必须转换为同一套标准交易记录，并保留原始来源证据。

本阶段不承诺“支持所有平台”。没有真实样本或无法可靠配对的格式必须安全阻断，不得猜测盈亏、时间、方向或费用。

## 用户任务

用户上传自己已有的交易记录后，系统应当：

1. 识别文件属于完整交易、订单流水、成交明细还是未知格式。
2. 识别可验证的平台和账户信息；无法验证时允许显示“未识别平台”，但不能伪造平台名称。
3. 预览标准化后的交易，并清楚列出缺失信息。
4. 只有在记录足以形成可靠交易结果时才允许保存。
5. 保存导入批次和来源证据，以便日后修正适配器时重新核对。
6. 从记录里的实际标的生成统计维度，不维护一份假装完整的市场标的菜单。

## 文件类型优先于平台

| 文件类型 | 典型内容 | 当前处理 |
|---|---|---|
| 完整交易记录 | 开仓、平仓、方向、标的、已实现结果 | 通过预览和确认后可导入 |
| 订单/成交历史 | 单独买入、卖出、撤单、部分成交 | 需要 FIFO、平均成本或来源指定的配对规则；完成前阻断 |
| execution/fill 历史 | position、fill、order、部分平仓 | 需要按仓位和成交顺序重建；完成前阻断 |
| 持仓快照 | 当前数量、成本、浮盈亏 | 只能作为持仓证据，不能当成已完成交易 |
| 资金流水 | 入金、出金、利息、平台调整 | 不能当成交易；未来进入账户资金流水模块 |
| 未知格式 | 无法可靠识别 | 提供字段映射或报错，不自动猜测 |

## 统一交易记录的最小字段

### 必须确认

- 用户与交易账户归属
- 原始标的和标准化标的
- 方向
- 开仓时间；本地时间必须确认来源时区
- 状态：持仓中或已平仓
- 可稳定去重的来源编号；没有编号时使用与文件名无关的稳定指纹

### 已平仓分析所需

- 平仓时间或可验证的平仓事件
- 来源报告的已实现盈亏
- 盈亏口径：毛盈亏、净盈亏或未知
- 费用状态：有明细、已包含但不可拆分、未提供
- 结果币种

### 可选增强

- 开仓价、平仓价、数量
- 止损、止盈、初始风险和实际 R
- commission、spread、swap、financing、tax 和其他费用
- 策略、setup、标签和备注

可选字段缺失不得被填成零。缺失与真实零值必须在数据层分开保存。

## 每次导入必须保存的批次证据

- `importBatchId`
- 原始文件名和文件格式
- 文件内容指纹
- 检测到的平台与检测置信状态
- 文件类型
- 用户选择的交易账户
- 来源时区及确认状态
- 盈亏和费用口径
- 总行数、有效行、错误行、重复行和实际新增行
- 导入器版本与导入时间
- 阻断原因或用户确认记录

当前已新增独立 `import_batch` 表和确认导入时的写入逻辑。预览只返回文件指纹与来源元数据，不创建数据库记录；文件通过预检且用户确认后才创建批次，避免预览操作制造垃圾记录。

该迁移目前只在可丢弃数据库副本上通过，尚未应用到真实本地或生产数据库。

## 导入决策

| 条件 | 保存交易 | 进入财务分析 |
|---|---:|---:|
| 完整交易、时间明确、净结果明确 | 是 | 是 |
| 完整交易、来源报告结果明确、费用已包含但不可拆分 | 是 | 是；标注“来源报告结果” |
| 已平仓但结果缺失或口径未知 | 暂缓 | 否 |
| 本地时间但来源时区未确认 | 否 | 否 |
| 订单或部分成交尚未配对 | 否 | 否 |
| 文件含错误行 | 整份暂缓，不做静默部分导入 | 否 |
| 重复上传 | 新增 0 笔并显示重复结果 | 不重复计算 |
| 未识别平台但标准字段完整 | 可通过通用映射预览；确认后保存 | 仅在全部财务门槛通过后 |

## 现有能力

- 文件格式：CSV、MT4 HTML。
- 已有字段映射：IC Markets、FTMO、MT4、MT5、cTrader、OANDA/FX Replay。
- 已能识别：完整交易记录、订单历史、execution/fill 历史、未知格式。
- 已有：来源时区确认、盈亏口径确认、费用符号确认、整文件错误阻断、稳定去重、交易账户归属检查。
- 已有交易字段：来源编号、来源标的、盈亏口径、费用拆分、来源时区、导入批次。

这些项目说明骨架已经存在，不代表所有列出的平台都经过真实用户文件验收。

## 当前缺口

### P1：数据可信度

1. `import_batch` 已保存文件指纹、来源平台、文件类型、适配器版本、确认口径和行数结果，但真实/生产数据库尚未执行迁移。
2. 每笔交易仍只保存宽泛的 `source=CSV/SCREENSHOT/MANUAL`；平台和文件类型目前通过批次关联追溯。
3. 订单与部分成交配对尚未实现；股票、加密和部分 MT5/cTrader 导出可能因此无法安全导入。
4. 每笔交易和导入批次现已保存结果币种及来源；未知币种或混合币种会阻断金额汇总。尚未实现汇率换算，也不会静默把不同币种相加。

### P2：适配与体验

1. 平台检测主要依赖表头命中数量，格式相似时可能误判。
2. 通用字段映射可以预览，但缺少清楚的“平台未知、文件仍可验证”状态。
3. 缺少可复用的适配器测试契约；新增平台时容易只验证解析，不验证盈亏、费用、时区和去重。
4. 缺少用户可见的导入历史、失败原因和重新映射入口。

## 平台适配器的最低验收

新增一个平台或格式时，只需要证明以下项目，不要求一次支持该平台的全部导出版本：

1. 文件类型识别正确。
2. 已知样本的交易数与来源一致。
3. 已实现盈亏、费用和币种与来源一致。
4. 时间按来源时区转换正确。
5. 同一文件重复导入新增 0 笔。
6. 缺失关键字段、未知方向、错误时间和未配对成交会被阻断。
7. 原始标的直接来自用户文件；不依赖预置的全市场标的列表。
8. 用第二份不同版本样本验证不会只对单一表头过拟合。

## 非目标

- 现在不建立“所有券商/交易所”下拉大全。
- 不为每个平台预先编写没有样本的映射。
- 不自动连接券商账户。
- 不从订单流水猜测完整交易。
- 不因平台无法识别就丢弃原始数据或伪造来源。
- 不在本阶段重做导入页面视觉设计。

## 推荐实施顺序

1. 建立独立导入批次与来源证据模型。
2. 把现有识别结果统一为平台无关的文件类型和可导入状态。
3. 为现有 FX Replay、MT4 和 Hyperliquid 夹具建立同一套适配器验收契约。
4. 用户提供新的真实脱敏文件时，再按样本增加或修正适配器。
5. 有足够的订单/成交样本后，再实现 FIFO、平均成本或仓位匹配。

第 3 项的第一版已经落地为 `check:import-adapters`：

- FX Replay 合成完整交易：允许保存。
- MT4 HTML 公开完整交易：允许保存。
- 通用订单历史合成数据：要求 lot matching 并阻断。
- Hyperliquid 公开 execution 数据：要求 position matching 并阻断。

合成夹具用于稳定验证契约，不能代替真实脱敏用户文件。以后新增平台时仍必须遵守“第二份不同版本样本”的最低验收要求。

结果币种规则已经落地为：

- 优先采用用户文件明确提供的结果/结算币种。
- 文件没有币种时采用所选交易账户币种，并把来源记录为 `ACCOUNT`。
- 币种不明、无效或同一分析范围出现多个币种时，不计算总盈亏、资金曲线等金额指标。
- 系统当前不做汇率换算；未来若加入换算，必须保存汇率来源、时间点和原始金额，不能覆盖原始结果。
